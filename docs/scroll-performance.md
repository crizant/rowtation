# Two-million-row scrolling investigation

For the later PR #8 renderer regression and its fix, see
[PR #8 grid scrolling regression](pr8-scroll-performance.md).

Measured on 2026-11-08. PR #6 reduced bridge work, but the main inertia-end
stutter is NSH 0.4.0 desktop scroll motion, not a long Rust row fetch. A separate
Inspector bug caused a real 127–160 ms main-thread pause. This change fixes that
Inspector pause. It does not claim to fix NSH's scaled scrolling.

## Controlled comparison

All variants were built with `nsh package --target web`, using NSH CLI 0.4.0
(`e626a8d`), locked crates, release WASM, and the browser's JavaScript engine.
The same file was imported through the real file input for every run:

- 2,000,000 rows, six text columns; 127,566,724 bytes (about 122 MiB).
- SHA-256: `96c01cb4c135f546a86ae805e456d8f0d837f7ce9f90ab02e6caf5de6e469f97`.
- Seven-digit unique IDs; 200 cities, 20 categories, amounts, boolean-like text,
  and short notes. Generated by `scripts/generate-scroll-fixture.py`.
- macOS ARM64, Brave (Chrome `156.0.8078.80`), headless, 1280 × 800, DPR 2,
  desktop idiom, approximately 60 Hz. The grid's scroll viewport was 672 px high.
- Before PR #6: `e319847`. After PR #6: `197f8e3`. Fixed: the same after-PR
  source with only `ProfileJob` ranking changed; the grid/cache code is unchanged.

The input protocol is identical: three descending pixel-wheel sequences, a tiny
wheel-delta sequence, then selection of the unique ID column while scrolling.
The Inspector is inactive during the first phases. These are reproducible CDP
wheel events, not a recording of a particular physical trackpad.

Three fresh-browser timing runs per variant used no method wrappers, CPU profiler,
or trace recorder. Frame intervals are **wall time between animation callbacks**,
not just the animation timestamp or the app's “next frame” diagnostic. The same
lightweight frame/movement sampling runs in all variants. Separate detailed runs
record method timings, CPU profiles, and Chrome layout/paint traces. Startup,
reading, inspection, and parsing are outside the measured scroll phases.

| Timing runs, ms (median across three runs) | Before #6 | After #6 | Inspector fix |
| --- | ---: | ---: | ---: |
| Grid-only frame interval, p50 | 16.6 | 16.7 | 16.7 |
| Grid-only frame interval, p95 | 20.3 | 19.7 | 19.2 |
| Largest frame during Inspector profiling | 141.2 | 139.0 | 34.9 |
| Range of largest grid-only frame across runs | 32.3–36.7 | 25.2–32.4 | 24.8–34.5 |

The small grid-only timing differences are not evidence of a meaningful smoothness
improvement. Occasional missed frames remain; this is not a zero-jank claim.

Detailed runs, with the same protocol:

| Work before selecting a column | Before #6 | After #6 | Inspector fix |
| --- | ---: | ---: | ---: |
| Rust row-window calls | 58 | 5 | 5 |
| Row calls including Rust→JS return conversion, total ms | 43.2 | 9.4 | 9.8 |
| Native component prop application, total ms | 10.6 | 3.3 | 3.4 |
| Largest native prop application, ms | 0.4 | 1.1 | 0.8 |
| Browser layout, total / largest event ms | 25.9 / 0.82 | 25.1 / 1.01 | 24.7 / 0.90 |
| Browser paint, total / largest event ms | 101.5 / 2.50 | 86.4 / 2.07 | 95.3 / 3.22 |
| Minor GC, total ms | 6.1 | 3.4 | 3.7 |

Native prop application wraps `nsh_browser_call(206, ...)`: it includes the
JS→NSH `DataTableRows::from_js` conversion and other component props, so it is an
**upper bound**, not an isolated row-conversion timer. NSH decodes all supplied
rows into its column storage on a data prop update; overlapping JS object identity
does not avoid that conversion. Its measured cost was too small to explain the
long pauses or stationary rows. Scroll handling inclusive of engine work peaked
at about 10 ms in these detailed runs. Browser layout/paint and GC did not account
for the long stall. Timings are inclusive where nested and must not be added.
Release WASM CPU samples have numeric function names, so these traces do not
separate Taffy layout from every other engine operation.

## NSH cause: motion stalls while frames continue

The relevant resolved NSH 0.4.0 sources are:

- `nsh-base/src/data_table/axis.rs`: `MAX_EXTENT = 3_000_000`, `Axis::ratio`,
  `content_offset`, and `content_offset_from`.
- `nsh-base/src/data_table/controller.rs`: `Dt::new` sets
  `anchored: !is_desktop()`; `offset_on` and `rest` choose the two behaviors.
- The packaged browser client (`nsh.js`): `wheel`, `scrollSmoothly`, `scrolled`,
  `ownEnd`, and `scrollEnded`.

At 34 px per row, the content is 68,000,000 px high. NSH exposes a 3,000,000 px
scroll extent. The desktop mapping is approximately:

```text
content offset = native scroll offset × (68,000,000 − 672) / (3,000,000 − 672)
               = native scroll offset × 22.67152
```

Unlike touch, desktop does not follow a local anchor. In the measured browser,
`scrollTop` rounded tiny requested offsets to whole CSS pixels. The rendered
content therefore moved in steps of about 22.5–23 px. During tiny input, rows
could stay still for about 200–250 ms and then jump, even though callbacks
continued about every 16.7 ms. This occurs inside an already-loaded cache range,
with no row fetch required. A frame-time-only benchmark misses this defect.

There is a second discontinuity in the same browser path:

```js
const smooth = e.deltaMode !== 0 || Math.abs(d) >= 40;
```

When a descending pixel-wheel stream falls below 40, `scrollSmoothly` cancels the
pending glide and immediately assigns its accumulated destination to `scrollTop`.
It catches up the unfinished glide in one step. One recorded transition moved
native offset 211 → 285 and displayed content about 1,678 px in one frame, with
no long frame. Scaling amplifies that catch-up. The threshold and direct assignment
explain why the disturbance is especially noticeable as inertia slows.

This is **not** an expensive desktop re-anchor at scroll end: `Dt::rest` returns
immediately on desktop. Timed `scrollEnded`/`ownEnd` calls were small. Touch uses a
different anchoring path and was not benchmarked here.

A proper upstream fix needs to preserve subpixel, one-to-one content motion for
wheel/touchpad input independently of the compressed absolute scrollbar position,
and avoid switching movement modes halfway through one pixel-wheel gesture.
Scrollbar dragging must still reach the entire dataset. Changing the cap, forcing
the touch idiom, intercepting wheel events in the app, or adding another cache
would mask or alter behavior without fixing that distinction. No such workaround,
NSH source edit, dependency patch, or version change is included.

## App fix: finish column profiling within the sliced work

`ProfileJob::step` previously limited counting to a row slice, then on its last
call walked **every distinct value** to choose the five common values. Selecting
the ID column walks two million distinct entries in that unsliced final stage.
It only runs after selection of an uncached column, not merely because the
Inspector is visible.

The fix retains five `(representative row, count)` leaders while counting. Each
changed count updates that tiny sorted list, preserving count-descending and
text-ascending tie order. The final call formats five previews instead of walking
the whole hash table. Text remains owned by the Rust document; no new dataset,
cache, worker, scheduler, or public API is introduced.

| Detailed profile run, ms | Before #6 | After #6 | Fix |
| --- | ---: | ---: | ---: |
| Final profile call | 127.4 | 131.5 | 4.4 |
| Largest profile call | 127.4 | 131.5 | 27.6 |

Hash-table growth and counting are still synchronous; the UI's adaptive 12 ms
target is not a hard deadline. The fix removes the unbounded finishing pass, not
all possible pauses. Exact unique counts and the five expected values were checked
through the production Rust/WASM bridge and visually in the Inspector.

The existing ranking test now checks 20,000 distinct values and late promotions,
comparing one-row, 137-row and whole-document slices against an independent full
sort. It retains the existing Unicode, empty-value and tie-order cases rather than
adding a duplicate test suite.

## Reproduce and check

Use Node 24+, Python 3, the project's NSH/Rust/WASM toolchain, and Chrome/Chromium
or Brave. Artifacts and generated data belong outside tracked files:

```sh
python3 scripts/generate-scroll-fixture.py /tmp/rowtation-profile/input.csv
nsh package --target web -o /tmp/rowtation-profile/fixed
node scripts/profile-scroll.mjs \
  --build /tmp/rowtation-profile/fixed/Rowtation \
  --csv /tmp/rowtation-profile/input.csv \
  --out /tmp/rowtation-profile/fixed.json \
  --browser '/Applications/Brave Browser.app/Contents/MacOS/Brave Browser' \
  --instrument --trace --cpu --max-profile-ms 50
```

For the A/B comparison, package detached worktrees at `e319847` and `197f8e3`
with the same CLI/toolchain, and run the same command on each production directory.
For frame comparisons, omit `--instrument --trace --cpu --max-profile-ms 50` and
repeat each variant three times. Use `--dpr 1` or `--dpr 2` explicitly when comparing
pixel rounding. The default is DPR 2, desktop, 1280 × 800. No dev server, test
clock, test host, cache-size change, or smaller dataset substitutes for the build.

The probe serves only the packaged directory over loopback, exposes its existing
player for observation, and imports the file with CDP's real file-input API. In
instrumented runs it wraps methods without changing their arguments/results.
It does not alter NSH source files. It samples applied row frames without forcing
browser layout. Output includes actual wheel events, frame wall times, native
scroll offsets, floating glide targets, displayed row positions, cache/native
conversion calls, long tasks, Inspector slices, and `tailMotion` movement steps/holds. Optional traces and CPU
profiles open in Chrome DevTools. `--screenshot <path.png>` saves visual evidence.

The optional 50 ms gate detects the old terminal pause on this host; it is not a
portable FPS guarantee or a default CI timing test. Check saved recordings with:

```sh
node scripts/profile-scroll.mjs --check /tmp/rowtation-profile/fixed.json \
  --max-profile-ms 50
```

The gate checks completion, exactly two million unique IDs, the correct five
values/counts, and the largest slice. The before-#6 and after-#6 detailed recordings
failed this gate (expected); the fixed recording passed. Raw CSVs, screenshots,
traces and recordings are local artifacts and are not committed.

Validation of this change: `cargo fmt --check`, native and wasm32 Clippy with
warnings denied, `nsh check`, `nsh build`, 46 passing headless tests (two existing
opt-in stress tests skipped), all 18 browser tests, and `nsh package --target web
-o dist` passed. The generated fixture's checksum was independently regenerated.
The production Inspector screenshot showed the correct 2,000,000 unique IDs and
five common values after scrolling.
